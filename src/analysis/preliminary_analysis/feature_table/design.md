# feature_table 設計書（特徴量の表と、相関で絞る）

2026-10-18 作成。決めた内容のすり合わせは 2026-10-16〜18（本人判断）。特徴量そのものの定義は `pretrained_encoders/design.md` §13 にあり、ここには書かない。

## 0. 目的と位置づけ

- 候補の特徴量 67 個（既存の 15 個 ＋ 新しい 52 個。`pretrained_encoders/design.md` §13.1）を、6 件のリポジトリの事前学習の区間で計算し、**表として書き出す**（§2）。
- その表を読んで、**相関の強い特徴量を落とし、残す特徴量の一覧を決める**（§3）。
- 表は、相関で絞ったあとも、事前学習（pretrained_encoders）・lookback_window・concept_drift_detection・concept_drift_cause が共通に読めるものにする。
  これらはすでに pretrained_encoders のレコード作り・特徴量作りを直接使っているので、表をどこか 1 か所の段階の中に置かず、独立したディレクトリにした（本人判断）。
- **2026-10-18 追記**：相関で絞ったあと、**事前学習も下流の 3 つ（窓長の調査・距離×時期行列・寄与度分析）も、特徴量はこの表から読む**（本人判断）。
  特徴量の計算は表を作るときの 1 回だけにし、値の出どころを 1 つにする。事前学習は事前学習の表だけを、下流は評価期間の表だけを読む（§2.1・§2.9）。
- 表を作る理由：相関の段階では、決まり（過半数か平均か）を変えて何度も出し直す見込みが高い。表がないと、出し直すたびに特徴量を最初から計算する
  （qtbase だけで準備と計算に約 1 時間半。`data/analysis/preliminary_analysis/timing_check/timing_qtbase.txt`）。表があれば数分で済む。

## 2. 表（build/）

### 2.1 期間と行
- **期間は事前学習の区間だけ**：データの始まり（そのリポジトリの最古の Change の作成時刻）〜 cutoff の版の公開日（`build_encoders.py` と同じ。`_resolve_cutoff`）。
  評価期間は今は入れない。後の段階が評価期間も表から読めるように、期間を足せる形（期間ごとに別のファイル）にしておく。
- **評価期間の表（2026-10-18 追加。本人判断）**：下流が使う範囲をまとめて 1 件につき 1 つ作る。
  - 範囲：**下流が使う最も早い日 〜 最後の評価の版の公開日**。最も早い日は、5 版それぞれについて、窓長の調査（最大の窓長）と
    距離×時期行列・寄与度分析（`binning.record_start`。使う窓長すべて）のレコード生成の開始日を下流と同じ関数で出し、その最小からさらに 7 日の余裕を引く。
  - **事前学習の表と重なってよい**。重ねて作るので、2 つの表をつなげて読むことはしない（境目でのレコードの重複・抜けの心配をなくすため）。
  - 行の決まりは事前学習の表と同じ（`record_builder.iter_records` に、上の範囲を `pool_start`・`cycle_end` として渡す）。
- **行は、今の事前学習が作るレコードと同じ**：0 時のレコードと、日の途中で Open になったレコード（`pretrained_encoders/design.md` §12.4）。
  0 時のレコードも最初の版より前は作らない（§12.4、2026-10-18 改めた）ことは、表を作る前に record_builder に入れる。
- 行の順番は (t, チケットの番号) の昇順にそろえる（毎回同じ表になるように）。

### 2.2 列
| まとまり | 列 | 型 | 中身 |
|---|---|---|---|
| 識別 | `change_id` | int64 | チケットの番号 |
| | `t` | datetime64[us] | 予測の時点（§12.4） |
| | `created` | datetime64[us] | チケットの作成時刻 |
| | `decision_time` | datetime64[us] | 最後に閉じた時刻（まだ Open なら NaT） |
| | `open_until` | datetime64[us] | t を含む Open の期間の終わり（閉じていなければ NaT） |
| ラベル | `label` | float64 | 正解ラベル（t から Δ 以内に人のレビューが付くか。`constants.TARGET`）。相関には使わないが、事前学習で使い回すときに要る |
| 特徴量 | `features` | float64 の (行数 × 67) | 並びは `feature_names`：既存の 15 個（`feature_builder.FEATURE_NAMES`）→ `TICKET_FEATURES`（13）→ `STATUS_FEATURES`（22）→ `WAITING_FEATURES`（17） |
| 代わりの値の印 | `filled` | bool の (行数 × 代わりの値がありうる特徴量の数) | 並びは `filled_names`。その行で、ふだんの定義で値が出ずに代わりの値（`pretrained_encoders/design.md` §13.2）を入れたら True |

- **精度は float64**（今の計算と値を完全に一致させるため。本人判断）。float32 にすると表は半分になるが、値がわずかにずれ、表から読んだ結果が今と変わりうる。
- 絞る前の **67 個を全部**入れる。絞ったあとは、読む側が列を選ぶ。
- **代わりの値の印はモデルには入れない**。値なしの印の列（missing indicator）は使わないと決めている（2026-10-17 本人判断）。印は、相関で絞るときの帳簿と、論文に書く割合のために持つ。
  - 印を持つのは、§13.2 の表に出てくる 20 個（既存の `merge_rate`・`recent_merge_rate`・`days_to_feature_release` と、`merge_ratio_60d`・`merge_ratio_total`・`ci_last_result`・`ci_fail_ratio`・`prior_reviewer_count`・`prior_message_count`・`ci_run_count`・`recheck_count`・`author_open_changes`・`file_days_since_change`・`avg_days_between_revisions`・`days_since_last_ci`・`avg_days_to_merge`・`avg_days_to_close`・`core_first_response_days`・`prior_first_response_days`・`non_core_change_ratio`）。
  - ~~既存の `days_to_feature_release` は、値が出せないとき −1 のまま（既存の 15 個は変えない）。今の期間では起きないことを確かめてあるが、起きたら件数を作った条件の記録（§2.5）に残す。~~
    **2026-10-18 改めた**：既存の 3 つ（`merge_rate`・`recent_merge_rate` は 0.0 → 0.5、`days_to_feature_release` は −1 → 観測の終わりまでの日数）も
    §13.2 の決まりで埋め、印を持つ（`pretrained_encoders/design.md` §11.1・§11.4）。`elapsed_time` の −1 はレコードでは起きないので変えない。
- 特徴量の計算は、代わりの値を入れたかどうかも返す形にする（`ticket`・`status`・`waiting` の各関数。値そのものは今と同じ定義）。

### 2.3 作り方（メモリ）
- **レコードを Python のオブジェクトで溜めず、数値の配列へ行ごとに詰めながら作る**（本人了承）。
  - 理由：今の `build_records` は全レコードをオブジェクトのリストで持ってから返す。qtbase の事前学習の区間は 0 時のレコードだけで約 337 万件の見込み（timing_qtbase.txt）で、
    67 個の特徴量をオブジェクトで持つと 10 GB を超えるおそれがある。このマシンのメモリは 16 GB。
  - 数値の配列なら、特徴量は 337 万 × 67 × 8 バイト ≈ 1.8 GB。
- やり方：
  1. `record_builder` に、レコードを 1 件ずつ返す形（ジェネレーター）を足す。今の `build_records` はそれをリストにしたものに置き換え、結果は今と同じにする。
  2. 1 件ごとに既存の 15 個と新しい 52 個を計算し、決まった行数（例 10 万行）の配列のかたまりに書き込む。かたまりがいっぱいになったら次のかたまりを作る。
  3. 最後にかたまりをつなげ、(t, 番号) で並べ替えて書き出す。
- 新しい 52 個の準備（全 Change の ChangeFacts、中核・開発状況の索引）は、リポジトリごとに 1 回だけ作る（今の作りどおり）。
- 1 件のリポジトリで失敗しても止めずに次へ進み、失敗したリポジトリと理由を最後にまとめて出す（黙って飛ばさない）。

### 2.4 形式と置き場所

  parquet は速さの差が数秒〜1 分程度で、pyarrow のインストールが要るので使わない。
- 文字列の配列（`feature_names`・`filled_names`）は unicode の配列で持ち、`allow_pickle=False` で読めるようにする。
- ファイル：`data/analysis/preliminary_analysis/feature_table/table/<project>/pretrain.npz` と、同じ場所の `pretrain_meta.json`（§2.5）。
  後で評価期間を足すときは ~~`eval_<版>.npz` のように期間ごとに分ける~~。
  **2026-10-18 改めた**：評価期間は 5 版をまとめて `eval.npz`・`eval_meta.json` の 1 つにする（§2.1。範囲を 1 つにすれば版ごとに分ける必要がない）。

## 3. 相関で絞る（selection/）

### 3.1 方針
- 目的は**多重共線性を除く**こと。重なった特徴量があると、後の IG（寄与）でその間に寄与が分けられて解釈を誤るため。
- **前例**：Khatoonabadi 2024（§2.4 Feature Correlation Analysis）は、非線形のモデル（CatBoost など）で、組の Spearman の順位相関だけで相関の強い特徴量を除いている。これに従う（本人判断）。
- **残す方の選び方**は AutoSpearman（Jiarpakdee・Tantithamthavorn・Treude 2018、ICSME。arXiv 1806.09791）の 1 段目に従う（本人判断）。
  - 原文の確認（2026-10-18）：論文の Algorithm 1 と §V、著者の R パッケージ Rnalytica の `get.automated.spearman.R`。両者は一致していた。
  - **2 段目の VIF（分散拡大係数）は使わない**（本人判断）。VIF は線形回帰の係数の推定が不安定になる度合いで、非線形のモデルには直接当てはまらない。前例の Khatoonabadi 2024 も使っていない。
    3 つ以上の組み合わせによる重なりは見ていない、と論文に限界として書く。

### 3.2 手順
1. **入力**：§2 の表の、事前学習の区間の**全レコード**（0 時のレコードと日の途中のレコード。独立ではないが全部使う。本人判断）。
   値は**代わりの値で埋めた後の値**（モデルに入るのと同じ値。本人判断）。67 個すべてを対象にする（本流か否か・作成の時刻も残るとは限らない）。
2. **リポジトリごとに** Spearman の順位相関行列を出す（各列を順位にし、同順位は平均の順位にして、ピアソンの相関を取る）。
3. **値が一定の列**（Qt の 3 件の `ci_last_result`・`ci_fail_ratio`・`ci_run_count`・`recheck_count` など）は ρ が出ない（標準偏差が 0）。
   そのリポジトリでは「**どれとも相関が強くない**」と扱い、判断はほかのリポジトリの値だけで行う（本人判断。AutoSpearman も定数の列を先に外している）。
4. **6 件をまとめて「相関が強い組」を決める**。決まりは次の 4 通りを全部出し、どれを採るかは後で選ぶ（本人判断）。
   - 過半数 k（k ＝ 3・4・5）：|ρ| ≥ 0.7 になったリポジトリが k 件以上の組（ρ が出ないリポジトリは「0.7 未満」に数える）
   - 平均：6 件の **|ρ| の平均**（ρ が出ないリポジトリを除いた平均）が 0.7 以上の組（ρ のまま平均すると符号が逆のリポジトリで打ち消し合うため |ρ|。本人判断）
   - **2026-10-18 決定：割合 2/3 を採る**（本人判断）。|ρ| ≥ 0.7 になったリポジトリが、**ρ が出るリポジトリの 2/3 以上**の組を「相関が強い組」とする
     （6 件そろう組は「6 件中 4 件以上」と同じ。値が一定で ρ が出ないリポジトリがある組だけ、出るリポジトリの数に同じ割合を当てる：3 件なら 2 件以上）。
     上の「過半数 k」は ρ が出ないリポジトリを「0.7 未満」に数えるので、CI の結果がある 3 件だけで重なる CI どうしの組を決して捉えられないため。
     中央値・平均より、リポジトリごとに出典の基準（0.7）で重なりを判定する割合のほうが、リポジトリごとにモデルを作る本研究に合う。
     保存済みの相関行列から試算した結果：残る 55 個・落ちる 12 個（「過半数 4」の 10 個 ＋ `ci_run_count`・`ci_fail_ratio`）。
     selection の出力（`selected.csv`・`steps_*.csv`）に割合の決まりを足し、保存済みの相関行列から当て直す使い方を足すのは後で行う（本人判断。事前学習を先に回すため）。
