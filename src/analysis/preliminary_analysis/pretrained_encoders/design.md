# pretrained_encoders 設計書（共有基盤：事前学習エンコーダ＋汎用ヘッドの作成・保存）

## 0. 位置づけ・要旨
- 集合 Transformer の**事前学習エンコーダ（表現）＋汎用ヘッド（仮予測ヘッド）を（プロジェクトごとに）一度だけ作って保存**し、下流の分析（まず `lookback_window`、将来は他分析も）が **load して使い回す**ための**共有基盤**。
- **対象は複数プロジェクト**（今回の論文は qtbase / qtcreator / wikimedia_mediawiki_core / qtdeclarative / go / typo3_cms の 6 件。2026-10-15 に OpenStack 6 件から切り替えた）。project を引数に取り、**プロジェクトごとに独立のエンコーダ群**を作る（§1, §7 の `PROJECTS`）。
- 前回（`concept_drift_detection`）は実行時にエンコーダを保存しておらず作り直しになった。その反省で**作成と利用を分離**する。
- **本ディレクトリを"基点（基盤）"とする**：モデル・データ構築・特徴・label・Scaler など必要な部品を**本ディレクトリ内に持つ**（他分析からの流用ではなく、ここを起点にして、下流はここを import／オーバーライドして使う）。`concept_drift_detection` の該当コードは**参考にしてよいが依存しない**（本ディレクトリを正とする）。
- 学習するのは**エンコーダ**と**汎用ヘッド**。下流は凍結エンコーダの上で線形ヘッドを貼り直す（＝チューニング。`lookback_window` §5）。汎用ヘッドは「チューニングしない汎用予測」の基準として下流でも使える。
- 用語：レビュー対象の単位は **Change**（Gerrit）で統一。

## 1. 事前学習データ（プロジェクトごとに 1 モデル）
- **対象プロジェクト**：今回の論文の 6 件（`PROJECTS`＝§7。選び方は `src/collectors/project_selection/design.md` §4「論文の対象」）。各プロジェクトで**独立に**エンコーダ＋汎用ヘッドを作る。
  OpenStack 6 件（nova / neutron / cinder / glance / keystone / swift）は今回の論文では分析しない。設定は `OPENSTACK_PROJECTS` に移して残す（§7。2026-10-15）。
- **プロジェクト開始 〜 そのプロジェクトの cutoff リリース日まで**の全計測点を使う。プロジェクト開始は、そのリポジトリの Gerrit の最古の Change（収集のデータの始まり）。
  cutoff は `PROJECTS` で project ごとに定義する。版の単位は**機能リリース**（新しい機能を含む定期的なリリース。選定の設計書 §5.2）で、**2025 年末までの直近 5 版を評価し、その 1 つ前を cutoff とする**。

  以前の OpenStack の cutoff：nova=25.0.0 / neutron=20.0.0 / cinder=20.0.0 / glance=24.0.0 / keystone=21.0.0 / swift=2.29.0。

## 2. 計測点・集合の単位・特徴・標準化（本ディレクトリに実装）
- 計測点 T ＝ 毎日 0 時（`MEASUREMENT_STEP_DAYS=1`）。各 T で **アクティブな Change 群**（`T-LOOKBACK <= created <= T` かつ **T に Open**）を 1 つの「集合」とする。Open かどうかは §11.1 の Open の期間で判定する（旧版は `T < decision_time`、decision_time＝最後の更新 `updated` だった）。
- 特徴は **15 種類**（`FEATURE_NAMES` と算出ロジックを本ディレクトリに持つ）。**どの特徴も T の時点で分かる情報だけで作る**（§11）。
  - **2026-10-18 改めた**：モデルに入れる特徴量は、相関で残したものの一覧 `features/feature_set.py` の `MODEL_FEATURES`（§12.5）。
    値は `feature_table` の表から読む（事前学習は事前学習の表。`feature_table/design.md` §2.6・§2.9）。
    `feature_builder.FEATURE_NAMES` は既存の 15 個の計算の並びとして残し、モデルの入力の並びには使わない。
  - **事前学習の集合は表から作る**（`build_records` で全レコードをオブジェクトのリストにしない）。特徴量が 15 個から増えると、qtbase の約 337 万件で
    メモリ 16 GB を超えるおそれがあるため。集合の特徴量は numpy の配列のまま持ち、`Scaler.fit` も配列から出す。集合は今の作りと完全に一致させる。
- 目的変数（事前学習の教師）：`reviewed_within_delta`、Δ=1 日（label ロジックも本ディレクトリに持つ）。
  - 「人間のレビュー」は `src/utils/bot_detection.md` §3 の決まり（`is_human_review_message`）で判定する。
    **2026-10-16 に §3 を改め、印（tag）のない自動の記録（Gerrit 本体の文・Qt のプラグインと古い改造版の文・書いた人がいないメッセージ）も除く**ことにした。
    改める前は印 `autogenerated:` だけで除いていたので、印の付かない年や Qt の「Staged for CI」「Precheck requested」などを人間のレビューと数えていた。
    特徴量（§13.2 の「人のコメント」）と同じ決まりを使う。
- **Scaler は本事前学習データで fit** し、統計量（mean/std）を**保存**する。下流はこの統計で transform するだけ（下流で再 fit しない）。

## 3. モデル：集合 Transformer（本ディレクトリに実装）
- `SetEncoder`（自己注意・**位置エンコなし**＝置換不変）を本ディレクトリに実装。
- 設定：`D_MODEL=128 / N_LAYERS=2 / N_HEADS=4 / FFN_DIM=256 / DROPOUT=0.1 / MAX_SET_SIZE=None`。
  - `MAX_SET_SIZE` は旧版 512（集合の先頭 512 件で打ち切り。無作為抽出ではない）。**2026-10 に上限なし（None）へ変更**。
    旧版の OpenStack では 1 日の最大が 480 件（nova/27.0.0）で一度も効いておらず、上限をなくしても結果は変わらない。
    全件を見るべきという方針に合わせる。1 日に数千件になるプロジェクトを足すときは改めて扱いを決める。
- 併せて `Head`（線形／MLP）・`Scaler`・`pretrain`・`embed_sets`・`train_probe` も本ディレクトリに持ち、**下流はここから import**する（＝基点）。

## 4. 事前学習手順（教師あり）＋汎用ヘッド
- **エンコーダ＋汎用ヘッド（線形の仮予測ヘッド）**で「Δ以内レビュー(0/1)」を予測し、`BCEWithLogitsLoss` で学習（`PRETRAIN_METHOD="supervised"`）。
- ハイパラ：`PRETRAIN_EPOCHS=20 / PRETRAIN_LR=1e-3 / PRETRAIN_BATCH_SETS=16`。
- **勾配累積（2026-10-19 追加。本人判断）**：1 バッチ（16 日）を `PRETRAIN_MICRO_SETS = 4` 日ずつに分けて順伝播・逆伝播し、勾配を足し合わせてから 1 回更新する。
  - **理由**：qtbase の事前学習が、メモリ不足で Mac ごと落ちた（Python 25〜32 GB、16 GB のマシン。2026-10-18〜19 に 2 回。2 回目はカーネルパニックで再起動）。
    qtbase は 1 日の集合が大きく（事前学習の区間で中央値 724・最大 2,073 件、16 日のバッチの最大の中央値 1,877 件。ほかの 5 件は最大 909 件以下）、
    自己注意のメモリは バッチの日数 × ヘッド数 × L² で増えるので、1 バッチの山が 10 GB 前後になる。4 日ずつなら約 4 分の 1。
    1 日だけでも最大の日で 1 GB 未満なので、小分けで足りる（集合の上限 `MAX_SET_SIZE` は付けない。全件を見る方針のまま）。
  - **2026-10-20 改めた：かたまりごとに GPU のキャッシュを空にする（本人判断）**。4 日ずつにしても、qtbase の seed3・4 は始めて 25 秒で
    メモリ不足になった（`logs/pretrain_qtbase_seed34_retry2.log`。上限 0.7 ≈ 8.29 GB に対し 8.05 GB）。測ると、原因は**かたまりの大きさではなく、
    PyTorch のキャッシュの積み上がり**だった：集合の大きさが日ごとに違うので、計算の後のメモリを再利用しきれずに抱え続ける。
    上の「1 バッチの山が 10 GB 前後」「4 日ずつなら約 4 分の 1」の見積もりも誤り（最初のクラッシュの 32 GB にはキャッシュが混ざっていた）。
    測定（qtbase の事前学習の表、seed3 と同じ順番、上限 0.7。スクラッチの測定用スクリプトで。リポジトリのコードは変えずに測った）：

    | 分け方 | 確保済みの領域の山 | 結果 | 1 バッチ |
    |---|---:|---|---:|
    | かたまり 1 つだけ：最悪の 4 日（2,073・2,068・2,064・2,059 件） | 3.05 GB（テンソル 2.03 GB） | 成功 | — |
    | かたまり 1 つだけ：最大の 1 日 | 1.04 GB（テンソル 0.56 GB） | 成功 | — |
    | 4 日ずつ（2026-10-19 の実装） | 2→4→6→8 GB と増える | 22 バッチ目でメモリ不足 | — |
    | 4 日ずつ＋バッチ（16 日）ごとに空にする | 7.09 GB | 150 バッチ成功（上限に近い） | 0.91 秒 |
    | 1 日ずつ＋バッチごとに空にする | 2.39 GB | 150 バッチ成功 | 1.20 秒 |
    | **4 日ずつ＋かたまりごとに空にする（採用）** | **3.10 GB** | **150 バッチ成功** | **0.94 秒** |

    バッチの終わりに生きているテンソルは 0.01〜0.03 GB だけ。`PRETRAIN_MICRO_SETS = 4` は変えず、`batch_backward` でかたまりの計算が終わるたびに
    `torch.mps.empty_cache()` を呼ぶ（MPS のときだけ）。数値には効かない。1 seed（20 エポック × 271 バッチ）で約 1.4 時間の見込み。
    回すときは `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.7` に加えて `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.6` も付ける
    （low は既定 1.4 で、high より大きいと始めにエラーで止まる。`logs/pretrain_qtbase_seed34_retry.log`）。
  - **同じ更新になるようにする**：損失は「16 日全体の有効な Change の数 N」で割る（各かたまりは「そのかたまりの損失の和 ÷ N」を逆伝播する）。
    勾配は和について線形なので、16 日をまとめて計算したときと数学的に同じ勾配になる。集合どうしは互いに影響しない（集合ごとに独立に符号化し、
    パディングは無視する）ので、かたまりごとのパディングの違いも結果に効かない。変わるのは dropout の乱数の引き方と浮動小数点の足し順だけ。
  - **全リポジトリで同じ作り**にする。~~ただし、勾配累積を入れる前に作った 5 件（qtdeclarative・typo3_cms・qtcreator・go・mediawiki）の 5 個と、
    qtbase の seed0〜2 は作り直さずに使い、qtbase の seed3・4 だけ勾配累積で作る（数学的に同じ手続きで、違うのは数値の誤差と乱数の引き方だけ。
    締め切りのため。本人判断 (a)）。~~
  - **2026-10-20 改めた：6 件すべてを作り直す（本人判断）**。
    - **qtbase の seed0〜2（2026-10-18 に勾配累積なしで作った）は、重みが NaN だった**（26〜27 か所。下流の埋め込みもすべて NaN）。
      ほかの 5 件の 25 個に NaN・無限大はない。下流の測定の途中で見つけた。
    - 調べたこと：qtbase の表（事前学習・評価）に NaN・無限大はない。標準化した後の極端な値（最大 489 倍）も qtcreator（440 倍）と同じくらい。
      初期のモデルでは、最大の日でも CPU と MPS で損失が一致し、NaN は出ない。新しい形（4 日ずつ＋かたまりごとに空にする）で seed0 と同じ乱数で
      3 エポック目の途中（650 バッチ）まで回して NaN なし（損失 0.13→0.10、勾配のノルム 0.06〜0.13、重みの最大 1.07）。
    - **原因は特定していない**。推測：古い形（16 日まとめて計算）は qtbase だけ Python 約 30 GB・スワップの状態になり、MPS がエラーを出さずに
      誤った値を返した。古い形を再現するには上限を外す必要があり、Mac が落ちたので再現はしない（本人了承）。
    - 5 件も古い形で作ったので、念のため新しい形で作り直し、6 件を同じ形・同じコードにそろえる（本人判断）。
    - **順番**：古いエンコーダ（6 件すべて）を `<OUTPUT>/<project>/cutoff_<cutoff>_old_20261018/` へ退避（消さない。qtbase の seed0〜2 は NaN の証拠）
      → qtbase の seed0〜4 → 続けて 5 件 × 5 個を **1 つのコマンド**で回す（qtbase 約 7 時間、5 件 4〜6 時間）。
      qtbase が終わった時点で Claude が確かめ（5 個とも NaN の点検を通ったか・汎用ヘッドの損失と AUC が妥当か・seed の間で外れがないか）、
      おかしければ本人が 5 件を止める（本人判断）。下流は 6 件そろってから回す。
  - **NaN の点検（2026-10-20 追加。本人判断）**：事前学習のバッチごとに、損失・勾配・更新後の重みが有限かを確かめる。
    非有限が出たら、その seed は**エラーで止め、保存しない**。ログと記録のファイル（`<OUTPUT>/<project>/cutoff_<cutoff>/seed<k>_nonfinite.json`）に、
    エポック・バッチの番号、損失・勾配・重みのどれか、そのバッチの集合の大きさを残す。次の seed は別のプロセスなので続けて回る
    （止めずに、飛ばしたものは必ず記録する決まりに合わせる）。
  - **安全装置**：回すときは環境変数 `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.7`（GPU が使えるメモリを約 7 GB までにする）を付け、
    超えたら Mac を巻き込まずに Python がメモリ不足のエラーで止まるようにする。これはこのマシンの都合なので、コードには書かずにコマンドに付ける（本人了承）。
- 学習後、**エンコーダを凍結**。**エンコーダと汎用ヘッドの両方を保存（両方とも必須）**。
- 汎用ヘッドの役割：下流での「**チューニングしない汎用予測**」の基準線・比較（`concept_drift_detection` §8.3 の汎用ヘッド相当）、および線形ヘッドの初期値としても利用可。

## 5. 反復（seed ＝ 別エンコーダ）
- `N_REPEATS` 個を作る（seed = `RANDOM_SEED + k`）。各 seed で **エンコーダ＋汎用ヘッド**を保存。
- 既定は 10 個（ばらつき・IQR 用）。下流は保存済みの seed 群を load する。

## 6. 保存フォーマット（＝下流との「約束事」・最重要）
出力先：`data/analysis/preliminary_analysis/pretrained_encoders/`

```
<OUTPUT>/<project>/cutoff_<cutoff>/seed<k>/
  encoder.pt        # 必須：SetEncoder の state_dict（torch.save）
  general_head.pt   # 必須：事前学習の汎用（仮予測）ヘッドの state_dict
  scaler.json       # 必須：{"mean":[...15...], "std":[...15...]}
  config.json       # 必須：下記メタ（下流はこれを読んで同一構成で再構築）
```

`config.json` の内容（例）：
```json
{
  "project": "nova",
  "cutoff": "25.0.0",            // = 26.0.0 サイクル開始の直前
  "seed": 0,
  "feature_names": [...15...],
  "feature_dim": 15,
  "d_model": 128, "n_layers": 2, "n_heads": 4, "ffn_dim": 256, "dropout": 0.1,
  "max_set_size": null,           // 上限なし（§3）
  "head_type": "linear", "head_hidden": 64,
  "pretrain_method": "supervised",
  "pretrain_epochs": 20, "pretrain_lr": 1e-3, "pretrain_batch_sets": 16,
  "review_horizon_days": 1,
  "measurement_step_days": 1, "lookback_days": 365
}
```

**load API（下流が呼ぶ想定）**：
```python
load_pretrained(project, cutoff, seed)
    -> (encoder: SetEncoder(eval,frozen), general_head: Head, scaler: Scaler, config: dict)
list_seeds(project, cutoff) -> [seed, ...]      # 保存済み seed の列挙
```
- 下流は `config` で `SetEncoder`／`Head` を同一構成に再構築 → `encoder.pt`／`general_head.pt` を load → `eval()`／凍結、`scaler.json` から `Scaler` を復元。
- **2026-10-18 追記**：`config.json` の `feature_names` は `MODEL_FEATURES`。`load_pretrained` は、保存した `feature_names` が今の `MODEL_FEATURES` と
  （並びも含めて）違えば**止めて知らせる**（旧版の 15 個のエンコーダなどを、黙って違う並びの入力で使わないため。本人判断）。
  止めるときは、事前学習を作り直すコマンドを示す。
- **2026-10-20 追記：重みの点検（本人判断）**：`load_pretrained` は、エンコーダ・汎用ヘッドの重みと Scaler の平均・標準偏差に NaN・無限大があれば止める
  （qtbase の seed0〜2 の NaN の重みを、下流がエラーなく読めてしまったため。§4）。止めるときは、どの seed のどの重みかと、作り直すコマンドを示す。
- **2026-10-20 追記：埋め込み（`embed_sets`）は 4 日ずつに分け、かたまりごとに GPU のキャッシュを空にする（本人判断）**。
  旧版は 16 日（`PRETRAIN_BATCH_SETS`）まとめて計算していた。qtbase の評価期間（1,224 日、集合の最大 1,465 件）で、16 日まとめると山 8.17 GB
  （上限 8.29 GB のぎりぎり）、4 日ずつ＋空にすると 1.07 GB（全日で 10.7 秒 → 25.3 秒）。集合どうしは互いに影響しないので値は変わらない
  （qtcreator の正常なエンコーダで、16 日と 4 日の埋め込みが完全に一致。差 0.0）。日数は定数 `EMBED_CHUNK_SETS = 4` にする。

## 7. パラメータ（constants に集約）
- 本ディレクトリに `constants.py` を持つ（基点）。事前学習・モデルの設定（`PRETRAIN_*`, `D_MODEL` 等, `N_REPEATS`, `RANDOM_SEED`, `MEASUREMENT_STEP_DAYS`, `LOOKBACK_DAYS`, `REVIEW_HORIZON_DAYS`）を集約。
- **`PROJECTS`（プロジェクト別設定）**：`project -> {"cutoff": <版ラベル>, "versions": [<5版>]}` の対応表を持つ。cutoff は事前学習の締め、versions は下流のチューニング対象（本ディレクトリでは cutoff のみ使用）。cutoff の**日付は `major_releases_summary.csv` から実行時に引く**。
  - 例：`{"qtbase": {"cutoff": "6.5.0", "versions": ["6.6.0",...,"6.10.0"]}, "go": {"cutoff": "go1.20", "versions": ["go1.21",...,"go1.25"]}, ...}`（今回の論文の 6 件。§1 の表）。
  - **`PROJECTS` には今回の論文の 6 件だけを置く**。OpenStack 6 件の行は **`OPENSTACK_PROJECTS`** という別の表に移して残す（2026-10-15 本人判断）。
    何も指定しなければ `PROJECTS` の 6 件だけが回り、OpenStack は `--project nova` のように名前を指定したときだけ引ける
    （設定を引く処理は `PROJECTS` → `OPENSTACK_PROJECTS` の順に探す）。

## 11. その時点で分かる情報だけで作る規則（2026-10 改訂）

### 背景
2026-10 にコードを点検したところ、計測点 T より後に起きることを使っている箇所が 4 つ見つかった
（§11.1〜§11.4。影響の大きさは nova の収集データ 44,359 件で実測）。分析を全部やり直すのに合わせて直す。
集合・特徴は学習に使う日にも評価日にも同じように作るので、どの日でも同じ規則が効く。

各特徴の「T の時点」は、その (Change, T) の T（その日の 0 時）である。評価日に限らない。

### 11.1 Open の期間（集合への出入り・open_ticket_count・merge_rate）

**旧版の問題**：マージ・放棄の時刻として `updated`（その Change に最後に何かが起きた時刻）を使っていた。
マージ後にも CI の結果や Zuul の通知、人間の "Cherry Picked"（安定版への取り込み）などが付くので、
`updated` は本当に閉じた時刻より後になる。「この後に記録が付くか」という未来の情報で、集合に入るかどうかが決まっていた。

```
nova  マージ 31,463 件の 84.6%、放棄 11,719 件の 9.9% で updated が本当の決着より後
      ずれ：中央値 0 日 / 上位 10% 2.6 日 / 上位 1% 118 日
      本来は閉じているのに集合に入っている (Change, 日)：101,308 件（閉じた Change の全 (Change, 日) の 4.6%）
      そのうち正例（マージ後の人間の記録による）：1,291 件（1.3%）
```

また、放棄されたあと復活する Change がある（nova 1,880 件。最後に放棄 891 件・最後にマージ 973 件）。
旧版は作成から最後の決着までずっと Open とみなしており、放棄から復活までの閉じている間も集合に入っていた。

**新しい規則**：Change の記録を時刻順にたどり、Open の期間の列を作る。

| 出来事 | 取り方 | Open の状態 |
|---|---|---|
| 作成 | `created` | 開く |
| 放棄 | 記録の 1 行目が `Abandoned` または `Patch Set N: Abandoned` のものの `date` | 閉じる |
| 復活 | 記録の 1 行目が `Restored` または `Patch Set N: Restored` のものの `date` | 開く |
| マージ | `submitted` | 閉じる |
| 後回し（Qt の Deferred。2026-10-16 追加） | 記録の 1 行目が `Deferred` のものの `date`（~~または `Patch Set N: Deferred`~~ 2026-10-16 改めた：古い形は出どころ不明のため使わない） | 閉じる |
| 後回しからの再開（Qt の Reopened。2026-10-16 追加） | 記録の 1 行目が `Reopened` のものの `date` | 開く |

- T が Open の期間 `[開いた時刻, 閉じた時刻)` のどれかに入るとき、その Change は T に Open とする。
  状態が NEW のまま終わる Change は、最後の期間を閉じない。
- nova では、放棄 11,719 件の全件で放棄の記録が見つかり、マージ 31,463 件のうち 31,461 件に `submitted` がある。
  取れない場合（`submitted` がない、状態が ABANDONED なのに放棄の記録がない等）は `updated` で代用し、
  件数をログに出す。記録の書き方の揺れ（tag `autogenerated:gerrit:abandon` 等）は実装時に全件で確かめる。
  ~~（2026-10-20 改めた：件数はリポジトリごとに出す。ログの頭にリポジトリ名を付け、出したら数えた帳簿を空にする。
  以前は帳簿を空にしなかったので、1 回の実行で複数のリポジトリを回すと、2 件目以降のログに前のリポジトリの分も足されていた。表示だけの問題で、値には効かない）~~
  （2026-10-20 改めた：**直すのは見送る**（本人判断）。帳簿（`review_utils.fallback_changes`）を空にしないため、1 回の実行で複数のリポジトリを回すと、
  2 件目以降のログの件数に前のリポジトリの分も足される。ただし表示だけの問題で、表の値には効かない。
  直す場所の `review_utils.py`・`record_builder.py` は表の指紋の材料（`feature_table/design.md` §2.5）なので、直すと作り終わった 12 個の表がすべて
  「指紋が違う」で止まる。このログが出るのは表を作るときだけなので、表を作り直す機会に直す。
  あわせて、値に効かない違いを本人が認めて指紋を付け替える道も後回しにした（止まったら、そのときに作る）。）
- **Qt の Deferred（2026-10-16 追加）**：Qt の Gerrit には、放棄とは別の状態 DEFERRED（後回し）がある。
  状態を作ったときの要求（Qt の課題票 QTQAINFRA-598）は「表示と絞り込み以外は放棄と同じ」とし、Qt の wiki（Gerrit Auto Cleanup）は
  「作業中の一覧から外れ、作業を再開するときに Restore で戻す」と案内している。Qt のプラグインのソースでも、放棄と同じ権限・同じ入力の形で行い、
  放棄の印（`TAG_ABANDON`）を付ける。Reopened は DEFERRED から NEW に戻す（`data/feature_survey/source_check9_untagged_messages_20261016.md` §2・§8）。
  そこで、**Deferred は放棄と同じく閉じる、Reopened は復活と同じく開く**とする。WIP（§12.1。状態は NEW のまま）とは違い、レビューの流れから降りる操作である。
  - 改める前は、Deferred の記録も状態 DEFERRED も見ていなかったので、DEFERRED のチケットを今日まで Open としていた。
    評価期間（2021〜2025 年）に誤って Open と数えた「チケット×日」は qtbase 1,498,933（1 日あたり約 820。集合の平均は 980）、
    qtcreator 319,319（約 175。同 323）、qtdeclarative 633,675（約 347。同 436）で、Qt の集合の 5〜8 割を占めていた
    （`data/feature_survey/deferred_check_result.txt`。DEFERRED のチケットの一覧は `deferred_changes.csv`、計 1,882 件で全件に Deferred の記録がある）。
  - 状態が DEFERRED なのに Deferred の記録がない場合は、ABANDONED と同じく `updated` で閉じ、件数をログに出す（2026-10-16 時点の 3 件のデータでは 0 件）。
  - 古い形の `Patch Set N: Deferred`（2013〜2014 年）の文は、出どころを確かめているところ（Qt の改造版 Gerrit を調べている）。
    状態 DEFERRED を作った時期（2013 年）と同じなので、閉じる扱いとする。
    **2026-10-16 改めた：古い形では閉じない。**Qt の改造版 Gerrit（qtqa/gerrit の stable-2.7-plus・V2.2.1-NQT-010・RC-V2.2.1-INT-022）の
    チケットの操作のファイルを見たが、Deferred の処理は見つからず、出どころが確かめられなかったため（本人判断）。
    影響は小さい見込み：この形の記録は Qt の 3 件で数百件ほど（上位の形で qtbase 165 件・qtcreator 43 件）、すべて 2013〜2014 年で評価期間の外。
    今も状態が DEFERRED のまま古い形の記録しかないチケットは、上の「記録がない場合は `updated` で閉じる」に当たり、状態の値で閉じる。
    閉じないままになるのは、古い形で後回しにされ、その後に再開・放棄・マージされたチケットの、後回しの間だけである。
  - 集合の大きさ（Qt の 3 件）は大きく変わるので、事前学習の前の議論（`MAX_SET_SIZE` など）では測り直した値を使う。
- `LOOKBACK_DAYS`（`T - created <= 365 日`）は変えない。
- 同じ Open の期間を次の 3 か所で使う。
  - **集合**：T に Open な Change だけを入れる（`record_builder`）。
  - **`open_ticket_count`**：T に Open な Change の数。旧版は「作成数 − 決着数」で、復活を考えていなかった。
  - **`merge_rate` / `recent_merge_rate`**：マージの時刻を `submitted` にする（旧版は `updated` で、マージを遅れて数えていた）。
    **2026-10-18 追記**：作者が数える期間に Change を 1 件も作っていない（`merge_rate` は t まで、`recent_merge_rate` は直近 90 日）とき、
    ~~0.0~~ **0.5** にする（§13.2 の「割合は 0.5」にそろえる。本人判断。実装は `fast_index.py`）。0.0 は「1 件もマージされない」という意味になり誤り。
    `merge_rate` はレコードの Change 自身が分母に入るのでほぼ起きない。`recent_merge_rate` は、レコードの Change が 90 日より前に作られて Open のままで、
    作者がその後 Change を作っていないときに起きる。

### 11.2 reviewed_lines_in_period

**旧版の問題**：「`updated` が過去 14 日以内にある Change」の「最終版の行数」を足していた。
- `updated` は収集時点から見た最後の更新なので、T の後にまた更新される Change は、14 日以内に活動していても数えられない。
  逆に数えられるのは「T の後はもう何も起きない」Change で、それは T の時点では分からない。
- 行数が最終版のもので、T の時点ではまだ存在しない版を使っていた。

```
nova の評価期間（2022-03-30〜2024-10-02、918 日）     旧版        新しい規則
  数える Change（1 日あたりの中央値）                   29 件        114 件
  行数（同）                                        2,650 行     19,278 行
  旧版の値 ÷ 新しい規則の値   中央値 0.16 / 日ごとの値の相関 0.35
```
（新しい規則の欄は「活動」に CI などの記録も含めて数えた値。採用した規則は下のとおり人間のレビューだけなので、件数はこれより少なくなる。）

**新しい規則**：
- 数える Change：`[T − 14 日, T]`（両端を含む。旧版と同じ）に**人間のレビュー**が 1 件以上ある Change。
  人間のレビューの判定は正解ラベル（§2）と同じ `review_utils.is_human_comment`（ボット・自動投稿・作成者本人を除く）。
- 行数：その Change の、T の時点で最新の版（`created <= T` のうち最新）の `lines_inserted + lines_deleted`。
- 意味：レビュアが手を付けた Change の量。CI が動いた量は含めない。

**人間のレビューの判定は変えない**：いまの判定には、レビューではない操作の記録も約 7% 入っている
（nova：本人以外によるパッチセットの追加 3.9%、編集の公開など 2.2%、放棄 0.6%、トピックの変更・取り込み・復活・取り消し 0.2%）。
何を除くかの線引きが難しいため、正解ラベルと合わせて今のままとする（旧版と同じ定義）。

### 11.3 bug_fix_confidence / refactoring_confidence

**旧版の問題**：Change の `subject` と、最新の版の説明文（`commit.message`）から判定していた。説明文は版を重ねると書き換わる。

```
nova で版が 2 つ以上ある Change 29,144 件
  全部の版に説明文が残っている        100%（収集で ALL_COMMITS を指定しているため）
  最初の版と最新の版で説明文が違う     55.8% ／ 件名が違う 23.4%
  バグ修正の判定が変わる              7.7% ／ リファクタリングの判定が変わる 6.2%
```

**新しい規則**：T の時点で最新の版（`created <= T` のうち最新）の `commit.subject` と `commit.message` から判定する。
版の選び方は、行数・ファイル数・テストの有無で使っている `_get_files_at_analysis_time` と同じにする。

### 11.4 days_to_feature_release（旧名 days_to_major_release）

**2026-10-15 改名**：「メジャーリリース」はリポジトリによって指す桁が違う（Qt は minor の x.y.0、MediaWiki・Go は major）ため、
**機能リリース（feature release）＝新しい機能を含む定期的なリリース**と呼ぶことにし、特徴量名と関数名
（`calculate_days_to_feature_release`）を変えた。値の計算方法は変えていない。

**旧版の問題**：リリースの表（`major_releases_summary.csv`）が版番号の形（`X.0.0`、swift は `2.Y.0`）で区切りを拾っていた。
- nova・neutron・cinder・glance・keystone は、2015-10-15 より前の版（`2011.2`・`2015.1.0` などの形）が表に入っておらず、
  その期間の値が「2015-10-15 までの日数」になっていた（例：2012 年 1 月の日で約 1,370 日。本来は数か月）。
- swift は 2014-07-07 より前（`1.x`）が入っていなかった。また 2020 年以前は 1 サイクルに `2.Y.0` が 2〜3 個あり、時期によって区切りの意味が変わっていた。
- 2025-10-01 より後は次のリリースが見つからず -1 になっていた（評価する期間は 2024-10 までなので、いまは使われない）。
- 誤った大きな値が事前学習のデータに入るので、標準化の標準偏差が膨らみ、元の値が正しい評価の期間でも標準化した値が狭い範囲に縮んでいた。
  また 2011〜2015 年のこの特徴は「何年ごろか」を表す値になっていた。

**新しい規則**：
- リリースの表をサイクル単位で作り直す（作り方は [src/collectors/README.md](../../../collectors/README.md) の「メジャーリリースの表」）。
  6 件とも OpenStack の公式のサイクルのリリース日を使う。swift も公式の日付に揃える。
  - **2026-10-15 追記**：今回の論文の 6 件（qtbase など）は、**正式版のタグの日**を機能リリースの区切りとする
    （`release_tags_collector.py`。選定の設計書 §5.2「区切りの日をタグから取る」）。OpenStack の行は YAML のサイクル単位のまま。
    どちらも同じ表に入り、この特徴量の計算方法は変わらない。
- その project の行の `release_date`（`status` が released・planned の両方）を日付順に並べ、**T より後の最初の日付**までの日数を返す。
  版番号は見ない。見つからなければ ~~-1（従来どおり）~~。
  **2026-10-18 改めた**：見つからなければ、**T から観測の終わり（そのリポジトリの全 Change の `updated` の最大。正解ラベルの観測の終わりと同じ）までの日数**
  （§13.2 の「まだ起きていない出来事までの日数は経過日数（下限）」にそろえる。次のリリースは少なくとも観測の終わりより後なので、本当の値の下限になる。本人判断）。
  関数 `calculate_days_to_feature_release`（`src/features/project_metrics.py`）に観測の終わりを渡す引数を足す（呼び出し元は `feature_builder` だけ。直してよいと本人）。
  今回の 6 件の事前学習の区間と評価期間では、T の後に必ず次の機能リリースが表にあるので、実際には起きない。
- T がリリース日の 0 時ちょうどのときは、そのリリースは済んだものとみなす（旧版と同じ）。
- まだ出ていないサイクルは予定日を使う。予定日は T の時点ですでに公開されているので、未来の情報にはあたらない。
- `RELEASE_LEVEL`（swift だけ `"minor"`）と、版番号から区切りを判定する処理（`_is_boundary_release` / `_release_ordinal`）は不要になる。

**分析期間の区切りへの影響**：事前学習の締め（`PROJECTS` の cutoff）と評価する 5 版の期間も同じ表から引く。
`PROJECTS` の版の書き方（`25.0.0`・`2.29.0` など）と出力先の名前は変えない。版番号で表の行を引き、日付は公式の日付を使う。
- nova 型の 5 件：公式の日付と版の日付が一致しているので、期間は変わらない。
- swift：区切りが swift の版の日付から公式の日付に変わるので、各期間が 2〜3 週間後ろにずれる（例：2.29.0 の締めは 2022-02-14 → 2022-03-30）。

### 11.5 変えないもの
- 正解ラベルの定義（T から 1 日以内に人間のレビュー。観測できない期間に掛かるものは除外）と、人間のレビューの判定（§11.2）。
- 行数・ファイル数・テストの有無・版数・経過時間（すでに T の時点の版から計算している）。
- 開発者の `past_report_count` / `recent_report_count`（T までの作成数）。
- 標準化の統計（事前学習のデータだけで計算）。

### 12.3 特徴量「作成の時刻」（`created_hour_utc`）
**足す時期**：特徴量を増やす作業のときに一緒に足す（§12 冒頭）。
- Change の作成の時刻の「時」を **0〜23 の整数（UTC）** で入れる（2026-10-15 本人判断。sin・cos の 2 つに分ける形は採らない）。
- 根拠：Khatoonabadi ら（2024, TSE）の Submission Hour（原文は未確認）。経過時間（`elapsed_time`）と組み合わせると、その日のうちに残された時間の長さを表せる。
- 「その日の終わりまでの残り時間」は、引用がないので特徴量にしない。
- 0 時に Open な Change も、その Change が最初に作られた時の値を入れる。復活した Change も、復活の時ではなく最初に作られた時の値。
- 0〜23 の整数なので 23 時と 0 時が遠い値になる（限界として認識しておく）。

### 12.4 その日に Open になった Change も入れる
**旧版**：日 d の集合は「日 d の 0 時に Open な Change」だけで、その日のうちに作られた Change は翌日の 0 時まで集合に入らなかった。
その日のうちに作られてマージされる Change は、一度も集合に入らなかった。

**新しい決まり**：日 d（UTC）ごとに、次の 2 種類のレコードを作る。

| レコード | 予測の時点 `t_i` | 特徴量 |
|---|---|---|
| 日 d の 0 時に Open な Change（今と同じ） | 日 d の 0 時 | 0 時の値（今と同じ） |
| 日 d の途中に作られた Change、または途中で復活した Change | 作成の時刻、または復活の時刻 | `t_i` の時点の値（作られたばかりなら経過時間 0・版 1 など） |

- **作られた Change の予測の時点は、「Change の作成時刻」と「最初の版（パッチセット 1）の作成時刻」の遅いほう**（2026-10-15 本人判断）。
  版の数・行数・ファイル数・件名などは「その時刻以前に作られた版」から作るので、最初の版が Change より 1 秒でも遅く記録されていると、
  作成時刻では「版がまだ 1 つもない（中身のない）Change」として予測してしまうため。ふつうは両者が同じで、そのときは作成時刻と変わらない。
  - 遅いほうの時刻が日 d の終わりを過ぎるなら、日 d の途中のレコードは作らない（翌日からは 0 時のレコードになる）。
  - 版の記録がない Change は、Change の作成時刻を使う。
  - 復活した Change には当てない（版はすでにあるので、復活の時刻のまま）。
  - 作られてから最初の版までの間（ふつうは秒単位）は、その Change はどの集合にも入らない。
    **2026-10-18 追記**：実装（`record_builder.py`）がこれを守っているのは日の途中のレコードだけで、0 時のレコードは作成時刻から作っていた
    （最初の版より前に 0 時をまたぐと、版のない 0 時のレコードができる）。**0 時のレコードも、最初の版の作成時刻より前は作らない**ように直す（本人判断。実装は未）。
    該当するのは下の「翌日以降にずれ込む」Change（qtbase 113・qtdeclarative 107・typo3_cms 61 件）。これで、レコードの Change 自身に「t に版がない」ことは起きなくなる（§13.2）。
  - ずれがある Change の件数とずれの大きさは、実装のあとに手元のデータで数えて報告する。極端なずれが多ければ扱いを改めて相談する。
    **数えた結果（2026-10-15、6 件の全期間）**：ほとんどの Change は両者がまったく同じ。版の記録がない Change、最初の版のほうが早い Change は 0 件。
    ずれがあるのは qtbase 272 件（0.21%。中央値 約 5 時間・最大 25.8 日）、qtdeclarative 300 件（0.54%。約 3 時間・14.9 日）、
    typo3_cms 71 件（0.12%。中央値 約 3.3 年・最大 5.7 年。記録が壊れているとみられる。推測）。qtcreator・mediawiki・go は 0 件。
    翌日以降にずれ込んで日の途中のレコードを作らないのは qtbase 113・qtdeclarative 107・typo3_cms 61 件。合わせて約 640 件（全体の約 0.1%）なので、
    この決まりのままとする。集計は `data/analysis/preliminary_analysis/set_size_check/first_revision_lag.py`・`first_revision_lag_result.txt`。
- **Open の期間の長さが 0 の Change**（作成と同時に閉じたことになっているもの。typo3_cms の 2013-06 より前など）は、どの時点でも Open ではないので、レコードを作らない（今の分析と同じ。2026-10-15 本人判断）。
- ちょうど 0 時 0 分 0 秒に作られた（復活した）Change は、0 時に Open な Change として 1 回だけ数える（二重に入れない）。
- 作成から 365 日を超えた Change を外す決まり（`LOOKBACK_DAYS`）は変えず、途中で Open になった Change にも同じく当てる。
- 途中で Open になった Change は、翌日以降は今までどおり 0 時のレコードになる。

**正解ラベル**：`(t_i, 日 d の終わり（UTC）]` に人間のレビューが付くか（2 値）。
- 0 時のレコードは `(0 時, 翌日 0 時]` で、今のラベル `(T, T+1 日]` と同じ。
- 途中で Open になったレコードは、窓が「その日の残り」に短くなる。
- 窓の終わりが観測の末尾を超えるレコードは、今と同じく作らない。

**文脈（Change i がどの Change を見て判断するか）**：Change j は、次の両方を満たすときだけ i から見える（自分自身は常に見える）。
1. `t_j ≤ t_i`（i より先に予測の時点が来ている）
2. `t_i` の時点で j がまだ閉じていない（j の Open の期間のうち `t_j` を含む期間の終わりが `t_i` より後。閉じていなければ見える）

例：0 時のレコードは、0 時に Open なレコードすべてを見る。10 時に作られた Change は、0 時のレコードのうち 10 時までに閉じていないものと、10 時までに Open になったレコードを見る。
**同じ時刻（秒まで同じ）に Open になった 2 件は、互いに見える**（どちらも「i 以前」に当たる。2026-10-15 本人判断）。

**集合のまとめ方**：レコードは予測の時点ではなく**日ごと**に 1 つの集合にまとめる（集合の時刻は日 d の 0 時）。集合には、各レコードの予測の時点と、
文脈の判定に使う閉じた時刻（そのレコードの予測の時点を含む Open の期間の終わり。閉じていなければなし）の列を持たせる。

**モデルの作り**：自己注意のマスクを、パディングだけを無視するマスクから、上の文脈の決まりを表すマスク（集合の大きさ L × L）に広げる。
- レコードに予測の時点 `t_i` と、文脈の判定に使う閉じた時刻を持たせ、集合をテンソルにするところ（`_pad_batch`）でマスクを作る。
- 1 日 1 回の順伝播で、全員分が正しい文脈で出る。下流の 3 分析は集合とモデルを本ディレクトリから import しているので、ほとんど直さずに済む。
  寄与度分析は、ロジットを計算するところ（`item_logits`）にマスクを渡す修正が要る。
- 1 日の集合は、その日に Open になった件数（6 件で 1 日 12〜32 件ほど）だけ増える。

### 13.2 共通の決まり
- **その時点で分かる情報だけ**：どの値も、予測の時点 t（§12.4。0 時のレコードは日の 0 時、途中で Open になったレコードはその時刻）までの記録だけで作る（§11）。

- **ボット**：今のボットの判定（`src/utils/bot_detection.md` の①〜④）。**ボットが作った Change は、出典が除いているもの（D6・D18・D26〜D28）だけ除き、ほかは数える**。
  2026-10-18 追記：D6 で作者がボットのときだけは、そのボットの Open なほかの Change を数える（値が出せないときの決まり。下の「値が出せないとき」）。
- **人のコメント**：ボットのメッセージと、Gerrit の自動の記録（`tag` が `autogenerated:` で始まるもの。版の作成の通知など）を除いたメッセージ。

## 14. 研究室のサーバで回す（2026-10-20 追加。本人判断）

### 14.1 目的
- 下流（窓長の調査・距離×時期行列・RQ2・寄与度分析）を研究室のサーバ（NVIDIA の GPU）でも回せるようにする。Mac より数倍速い見込みで、
  Mac で事前学習を回している間に下流を先に進められる。寄与度分析の範囲にも効く。
- サーバの仕様（機種・台数・メモリ・場所など）は、外に出してよい情報かわからないので、リポジトリには書かない（本人判断）。
  研究室で共有しているので、**使う資源は全体の 1/4 程度まで**にする（本人判断）。

### 14.2 置き場所（古い構成には触らない）
- 古い構成のディレクトリの隣に、新しく **`review_priority_v2`** という名前で GitHub から clone する（本人判断）。古い構成には触らない
  （以前の構成が入り組んでいて、古いファイル・古い結果・古い依存を黙って使う事故を避けるため。サーバにしかないデータもそこに残る）。
  - 古い構成の中の入れ子のディレクトリ（古い `docker-compose.yml` のつなぎ先として Docker が作った root 所有の空のディレクトリ）は、
    書き込めず、古いコンテナから入れ子で見えてしまうので使わない。

  時刻が変わると表が「指紋が違う」で止まる。

### 14.3 Docker（リポジトリにサーバ用の別ファイルとして入れる。本人判断）
- `Dockerfile.server`・`docker-compose.server.yml`（Mac 用の `Dockerfile`・`docker-compose.yml` は変えない）。
- コンテナ名 `review_priority_v2`（古いコンテナ `review_priority` とぶつけない）。つなぐのは新しいディレクトリだけ（`.` → `/work`）。
  依存のボリュームも古いものと分ける。
- 資源の制限：CPU とメモリは全体の 1/4 程度。値はサーバの上の `.env`（git の対象外）に `SERVER_CPUS`・`SERVER_MEM_LIMIT` として書き、
  `docker-compose.server.yml` はそれを読む（サーバの仕様をリポジトリに残さないため。本人判断）。GPU は 1 枚を渡す。
  **GPU は Docker では 1/4 に分けられない**（分割の機能がない GPU のため）。メモリだけ PyTorch の側で 1/4 に制限する（§14.4）。
  計算の速さは分けられないので、ほかの人が同時に使うと時間を分け合う（夜間に回す・研究室で声をかける等、運用で調整する）。
- PyTorch は、サーバのドライバが対応する CUDA の版に合うものを、PyTorch の公式の CUDA 版の置き場から入れる（新しい PyTorch をそのまま入れると
  新しい CUDA 向けになり GPU を使えないことがある）。版は Mac と同じ（torch 2.13.0）にそろえ、合う版がなければ、入れるときに確かめて決め直す

- コンテナから GPU を使うには、サーバに NVIDIA Container Toolkit が入っている必要がある（立てるときに確かめる）。

### 14.4 コードの変更
- `resolve_device`：`DEVICE = "auto"` のとき **CUDA → MPS → CPU** の順に選ぶ。CUDA を選んだら
  `torch.cuda.set_per_process_memory_fraction(CUDA_MEMORY_FRACTION)`（0.25）を一度だけ呼ぶ。
  今日の測定の山（事前学習 3.10 GB・埋め込み 1.07 GB・IG 8 段階ずつ 2.07 GB。§4・§6・`concept_drift_cause/design.md` §2.4）は、この上限に収まる見込み。
- `release_device_cache`：CUDA のときは `torch.cuda.empty_cache()`、MPS のときは `torch.mps.empty_cache()`、CPU では何もしない。数値には効かない。
- 保存したエンコーダは `map_location` で読むので、Mac（MPS）で作ったものをサーバ（CUDA）で読める（`load_pretrained` はそのまま）。
- MPS の環境変数（`PYTORCH_MPS_*_WATERMARK_RATIO`）はサーバでは要らない。
- これらのファイル（`model/set_transformer.py`・`utils/constants.py`）は表の指紋の材料ではないので、作り終わった表はそのまま使える。
