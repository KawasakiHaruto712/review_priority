# release_best_size 設計書：リリースごとに適した日数 N（2026-10-27 作成。本人判断）

## 0. 位置づけ・要旨

- 論文 4.4・5.4「リリースごとに適した日数N」のための分析。
  - 4.1 では、5 つのリリースをまとめて、N をリポジトリごとに 1 つの値に固定した。
  - 2.3 では「学習に適した期間はリリースや評価時期によって異なりうる」と述べている。それを確かめる。
- 時間による選び方と特徴空間による選び方のそれぞれで、**リポジトリ × リリース × 評価時期（6 × 5 × 3 ＝ 90 マス）ごとに、6 通りの N のうち平均 F1 値が最も高いもの**を求める。
  - 求めた N を、4.1 で選んだ N と比べる。
- **ほかの分析の出力ファイルを読むだけ**。モデルは動かさず、学習もし直さない。コードは import せず、ほかの分析と同じく独立させる。
- 対象は **重みあり版（posw）だけ**。重みなし版は、本人が言うまで封印する。

## 1. 読むもの（重みあり版。`data/analysis/preliminary_analysis/` の下）

| 中身 | 時間による選び方 | 特徴空間による選び方 |
|---|---|---|
| 評価日 × N × seed の指標 | `lookback_window/posw/<repo>/<版>/metrics.csv`（N の列は `window`） | `feature_space_window/posw/<repo>/<版>/metrics.csv`（N の列は `size`） |
| 評価日 → 評価時期 | `concept_drift_detection/posw/<repo>/set_transformer/<版>/daily_metrics.csv.gz` の `day`・`position` | `feature_space_window/posw/<repo>/feature_distance/<版>/daily_metrics.csv.gz` の `day`・`position` |
| 4.1 で選んだ N | `lookback_window/posw/report/selected_window.json` | `feature_space_window/posw/report/selected_size.json` |

- **N の候補**は 6 通り：`1d`・`3d`・`1w`・`2w`・`1M`・`2M`。両方の選び方で、全 30 版について 6 通りがそろっていることを確かめた（10/27、読むだけ）。
  - 時間の `metrics.csv` には、学習し直さない行（`window ＝ general`）も入っている。これは N の候補ではないので**使わない**。
- 使う列：`day`・N の列・`seed`・`missing`・`missing_reason`・`f1_plugin`。
- 版の一覧は、フォルダから取る。`concept_drift_detection` の `PROJECTS` に書かれた 5 版と一致することを確かめる。

## 2. 評価時期の割り当て（精度表と同じ）

- 評価時期は、精度表（論文の表 5）と同じ区切りにする。1 つ前のリリースから当該リリースまでを 3 等分する。
- **区切りを決める処理は書かない**。精度表の出力（`daily_metrics.csv.gz`）に保存された `day → position` の対応を、そのまま読む。
  - 時間の対応と特徴空間の対応は、同じ日で一致する（10/27、3 版で確かめた）。全版で一致することを、読むときに確かめる。一致しなければ止める。
- **評価日の範囲の違い**：`metrics.csv` には、当該リリースの日（`ce`）が 1 日だけ多く入っている。精度表の評価日は `[ce − 刻み × 3, ce − 1]` である（`concept_drift_detection/dataset/binning.py` の `position_of_days`）。
  - この日は精度表のどの評価時期にも入らないので、**使わない**（各版 1 日、全 30 日）。
  - 4.1 の N を選んだ平均（`summary_f1_plugin.csv` の `Ave`）には、この日も入っている。
- **番号の向き**：保存物の `position` は、p0 ＝ リリース直前（後期）の向きである。出力では **表示の向き `position_display ＝ 2 − position`**（p0 ＝ 初期。論文と同じ）を使う。
  - CSV には両方の番号と「初期・中期・後期」の名前を書き、取り違えを防ぐ。

## 3. 日ごとの値（3.4・4.1 と同じ決まり）

- 評価日 × N ごとに、**5 seed の F1 値（`f1_plugin`）の中央値**を取る。欠けた seed（`missing ≠ 0` または NaN）は除く。
  - 5 seed とも欠けた（評価日 × N）は値なしとする。
- 欠ける理由は 2 つある（10/27 に数えた）：
  - `eval_single_class`：評価日に正例か負例がない。どの N でも欠ける。全 244 日。
  - `train_single_class`：学習に用いる日に正例か負例がない。ほぼ `1d` だけで起き、`3d`・`1w` でも少し起きる。
    - 一部の N だけが欠けた日は、時間 182 日・特徴空間 110 日。

## 4. 最良の N の決め方（4.1 と同じ決まり。本人判断 10/27）

- 各マス（リポジトリ × 版 × 評価時期）× N について、次の 3 つを出す。
  - **平均**：日ごとの値の平均。
  - **標準偏差**：日ごとの値の評価日方向の標準偏差（ddof ＝ 1）。
  - **使った日数**
- **欠けた日の扱い（Q1 案 a）**：**N ごとに、その N で値が出た日だけを平均する**。すべての N で値が出た日にはそろえない。
  - 4.1（`lookback_window/design.md` §11.1）と同じ決まりである。
  - 4.1 の N と違った理由が、決まりの差にあると言われないようにするため。
- **同点の扱い（Q2）**：`lookback_window/evaluation/select_best.py` の `pick_best` と同じにする。
  - 平均を丸めずに比べ、最大のものを選ぶ。
  - 同じなら、標準偏差が小さい方を選ぶ。
  - それでも同じなら、N の短い順で最初のものを選ぶ。`pick_best` は表の行の順で選ぶので、ここでは順を固定する。
- 平均が 1 つも出ないマス（全 N で値なし）は、最良なしとする。出力に残し、件数を記録に書く。

## 5. 出力（`data/analysis/preliminary_analysis/release_best_size/posw/`）

| ファイル | 中身 |
|---|---|
| `best_size.csv` | 1 行 ＝ 選び方 × リポジトリ × 版 × 評価時期（2 × 90 ＝ 180 行）。列は下の通り |
| `best_size.md` | 人が読む表。表示の向きで、選び方ごとに 30 行 × 3 列。4.1 の N と違うマスに印を付ける |
| `best_size_table.tex` | 論文用の表（§5.1） |
| `summary.json`・`summary.md` | 本文用の集計（§6） |

- **`best_size.csv` の列**（Q3。紙面に載らなくても残す）：
  - キー：`method`（`time_distance`・`feature_distance`）・`project`・`version`・`position`（保存物の向き）・`position_display`・`phase_name`（初期・中期・後期）
  - N ごとの値：`mean_<N>`・`std_<N>`・`n_days_<N>`（6 通りの N それぞれ）
  - 最良の N：`best`・`best_mean`
  - 4.1 で選んだ N：`selected`・`selected_mean`
  - 差：`diff_best_minus_selected`（最良が 4.1 の N なら 0）・`is_selected_best`
  - 日数：`n_days_any`（どれかの N で値が出た評価日の数）

### 5.1 論文用の表（`best_size_table.tex`）

- 行はリポジトリ × リリース（30 行）。リポジトリ名は `\multirow` で 5 行にまとめる。
- 列は、時間 p0・p1・p2 と、特徴空間 p0・p1・p2 の 6 列（表示の向き）。
- 各マスには最良の N だけを書く（1日・3日・1週・2週・1ヶ月・2ヶ月。論文 4.1 と同じ書き方）。F1 値は載せない。
- **4.1 で選んだ N と違うマスは太字**にする。
- 表の下の注に、マスあたりの評価日の範囲（`n_days_any` の最小〜最大）を書く。最も少ないのは typo3_cms 13.4.0 のマスで、9〜10 日の見込み。
- まず 30 行で作り、紙面に収まらなければ後で決める（Q4。後回し）。
  - 代わりの案：18 行（リポジトリ × 評価時期）にし、5 リリースで最良になった N の種類の数を載せる形。

## 6. 本文用の集計（`summary.json`・`summary.md`）

選び方ごとに、次の 4 つを出す。

1. **同じ評価時期で、5 リリースの最良の N がすべて同じだった「リポジトリ × 評価時期」の数**（18 のうち）。5.4 の本文の柱。
2. 「リポジトリ × 評価時期」ごとに、5 リリースで最良になった N の種類の数。その分布（1〜5 種類がそれぞれ何件か）。
3. 最良の N が 4.1 で選んだ N と一致したマスの数（90 のうち）。
4. `diff_best_minus_selected` の中央値と最大値。本文には紙面の都合で載せない見込み（本人）。

- 本文には数だけを書き、「多い」「少ない」などの評価の言葉は使わない（結果の章の決まり）。

## 9. テスト

- 置き場所：`tests/analysis/preliminary_analysis/release_best_size/`。gitignore されているので `git add -f` で足す。
- 小さな作り物の表で、次を確かめる。
  - seed の中央値
  - N ごとに日がそろわないときの平均
  - 同点のとき標準偏差で選ぶこと
  - 全 N が欠けたマス
  - 表示の向き
  - リリースの日（精度表にない日）を使わないこと
- 実データで、次を確かめる。
  - 全 6 リポジトリ・全 30 版で、6 通りの N がそろっていること。
  - 時間と特徴空間で `day → position` が一致すること。
  - リリースの日を足して版全体を平均すると、4.1 の要約表（`summary/summary_f1_plugin.csv` の各版の値）と一致すること。読み方の誤りを見つけるため。

## 10. 限界として書くもの

- **評価日が少ないマスがある**。typo3_cms 13.4.0 は 1 マス 9〜10 日で、少ない日数で最良が決まっている。表の注に日数の範囲を書いて隠さない。
- **N ごとに平均に使う日が少し違う**。主に 1 日（4.1 と同じ決まり。§4）。
- **4.1 の N の値は、精度表の d0 と少しだけ違う**。
  - 精度表の d0 と、ここで読む N 別の結果（`lookback_window`）は、学習に用いるチケットは同じである（10/27 に go1.21 と qtcreator 15.0.0 で確かめた。正例・負例の数が全行で一致）。
  - 分類層は別々に学習しているので、F1 値は少し違う（版の平均で 0.002 程度）。
  - そのため、本分析の `selected_mean` と表 5 の d0 の値は、完全には一致しない。
- 90 マスごとに 6 通りを比べるので、差がわずかなマスでも最良は 1 つに決まる。差の大きさは CSV（`diff_best_minus_selected`）で確かめられる。
